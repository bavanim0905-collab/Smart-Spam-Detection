1. Introduction

1.1 Overview

In the digital age, Short Message Service (SMS) remains a critical communication channel for banking alerts, two-factor authentication (2FA), and personal communication. However, this ubiquity has made SMS a prime target for spammers and cybercriminals. Users are inundated with unsolicited marketing messages ("Robotexts") and malicious phishing attempts known as "Smishing" (SMS Phishing).

SpamScanner is a privacy-first Android application designed to combat this menace. Unlike traditional spam filters that rely on cloud-based APIs—compromising user privacy by uploading messages to external servers—SpamScanner employs an On-Device Machine Learning approach. By leveraging TensorFlow Lite, the application analyzes message content locally on the user's device, ensuring that sensitive personal data never leaves the phone.

1.2 Problem Statement

Current solutions for SMS filtering suffer from significant drawbacks:

  • Privacy Risks: Many apps upload message content to cloud servers for analysis, exposing financial alerts and personal conversations to third parties.
  • Latency: Cloud-based analysis requires an active internet connection and introduces network latency, delaying the delivery of legitimate messages.
  • Static Filtering: Keyword-based filters (e.g., blocking "winner") are easily bypassed by spammers using obfuscation (e.g., "w1nner").

1.3 Proposed Solution

SpamScanner addresses these issues through a hybrid approach:

  • Local Inference: A pre-trained Neural Network (TensorFlow Lite) runs directly on the Android device.
  • Contextual Understanding: The model understands semantic context, not just keywords, allowing it to detect sophisticated phishing attempts.
  • Seamless Integration: The app integrates with the Android telephony layer to intercept and classify messages in real-time without user intervention.

3. System Analysis

3.1 Functional Requirements

  1. SMS Interception: The system must listen for the android.provider.Telephony.SMS_RECEIVED broadcast to capture incoming messages immediately.
  2. Text Classification: The system must tokenize the message body and pass it to the TFLite interpreter. It must classify the message into one of three categories:
    • HAM: Legitimate personal or business messages.
    • SPAM: Unsolicited marketing or promotional content.
    • SMISHING: Malicious attempts to steal credentials.
  3. Inbox Management: Users must be able to view, search, and delete messages. Threads should be grouped by sender.
  4. Notification System: High-risk messages (Smishing) should trigger a distinct alert, while Spam should be silently filed away.

3.2 Non-Functional Requirements

  • Privacy: Zero data exfiltration. No internet permission is required for the core classification logic.
  • Performance: Inference time must be under 200ms on mid-range devices to prevent blocking the UI thread.
  • Battery Efficiency: Background services (WorkManager) must respect Android's battery optimization guidelines (Doze mode).

4. System Design

4.1 Architectural Pattern

The application follows the Model-View-ViewModel (MVVM) architecture recommended by Google. This ensures separation of concerns and testability.

  • View (UI): Composable functions (e.g., InboxScreen, ConversationScreen) that react to state changes.
  • ViewModel: Manages UI state and communicates with the Repository/Database. It survives configuration changes (screen rotations).
  • Model (Data): The single source of truth, consisting of the Room Database and the TFLite Classifier.

4.2 Database Design

The local database is managed by Room. The primary entity is SmsMessage.

4.3 Class Design

  • SmsApp: The Application class that initializes the Database and Classifier singletons.
  • SmsReceiver: A BroadcastReceiver that acts as the entry point for new messages.
  • SmsClassifier: A singleton object wrapping the TensorFlow Lite interpreter. Handles tokenize() and predict().
  • MainActivity: The single Activity hosting the Jetpack Compose navigation graph.

5.2 The Spam Classifier Engine

The heart of the application is SmsClassifier.kt. It loads the .tflite model from assets and performs inference.

Tokenization

Neural networks cannot understand raw text. We convert text into a sequence of integers using a vocabulary mapping.

private fun tokenize(text: String): IntArray {
    val words = text.lowercase().split(Regex("\W+"))
    // Map words to indices, use  (Out Of Vocab) if unknown
    val tokens = words.map { vocab?.get(it) ?: vocab?.get("") ?: 1 }

    val arr = IntArray(maxLen) { 0 }
    val start = maxLen - tokens.size

    // Pad or Truncate to fixed length (200)
    for (i in tokens.indices) {
        if (start + i >= 0 && start + i < maxLen)
            arr[start + i] = tokens[i]
    }
    return arr
}

Inference

The predict function runs the model on the tokenized input.

@Synchronized
fun predict(text: String): Pair {
    val tokens = tokenize(text)
    val byteBuffer = ByteBuffer.allocateDirect(maxLen * 4)
    byteBuffer.order(ByteOrder.nativeOrder())
    
    // Fill buffer
    for (token in tokens) {
        byteBuffer.putFloat(token.toFloat())
    }

    val output = Array(1) { FloatArray(3) } // [HAM, SPAM, SMISHING]
    model?.run(byteBuffer, output)

    val result = output[0]
    val index = result.indices.maxByOrNull { result[it] } ?: 0
    val labels = arrayOf("HAM", "SPAM", "SMISHING")
    
    return Pair(labels[index], result[index])
}

5.3 Handling Incoming SMS

When an SMS arrives, the SmsReceiver intercepts it. To avoid blocking the main thread (which would freeze the phone UI), we delegate the heavy lifting to WorkManager.

class SmsReceiver : BroadcastReceiver() {
    override fun onReceive(context: Context, intent: Intent) {
        if (Telephony.Sms.Intents.SMS_RECEIVED_ACTION != intent.action) return

        val msgs = Telephony.Sms.Intents.getMessagesFromIntent(intent)
        val smsText = msgs.joinToString("") { it.messageBody }

        // Schedule background job
        val workRequest = OneTimeWorkRequestBuilder()
            .setInputData(Data.Builder().putString("sms_text", smsText).build())
            .build()

        WorkManager.getInstance(context).enqueue(workRequest)
    }
}

7. Future Enhancements

While the current system is robust, several features are planned for future versions:

  1. Multilingual Support: Retraining the TFLite model on a diverse dataset to support Hindi, Spanish, and French spam detection.
  2. Crowdsourced Blacklist: A feature allowing users to report spam numbers to a central server (anonymized), creating a community-driven blocklist.
  3. User Feedback Loop: "Report as not Spam" button to correct the local model and improve accuracy over time.
  4. Wear OS Integration: Viewing spam alerts directly on smartwatches.

8. Conclusion

The SpamScanner project successfully demonstrates the feasibility and effectiveness of running advanced machine learning models directly on mobile devices. By shifting the processing from the cloud to the edge, we have achieved a solution that is private, fast, and offline-capable.

The application effectively filters out noise from the user's inbox, identifying high-risk phishing attempts with high accuracy. The use of modern Android development practices (Compose, Room, Coroutines) ensures the codebase is maintainable and scalable. This project serves as a solid foundation for a comprehensive personal security suite.
